# @cuongcds/open-analytics

[![npm](https://img.shields.io/npm/v/@cuongcds/open-analytics)](https://www.npmjs.com/package/@cuongcds/open-analytics)
[![jsDelivr](https://data.jsdelivr.com/v1/package/npm/@cuongcds/open-analytics/badge)](https://www.jsdelivr.com/package/npm/@cuongcds/open-analytics)

A small, dependency-free client-side tracker: page views, clicks on
elements carrying a `data-track` attribute, and search-form submits. Ships
as plain `<script>` tags — no framework required, and no build step needed
to *use* it (drop `src/*.js` straight into a page, or load it from a CDN —
see "CDN (jsDelivr)" below). A minified `dist/` build is included for
production use; see "Building" below.

Pairs with [`ci3-analytics`](https://github.com/cuongcds/ci3-analytics) for
a CodeIgniter 3 backend, but the endpoint it posts to can be anything that
accepts the same `application/x-www-form-urlencoded` payload.

## Installation

```bash
npm install @cuongcds/open-analytics
```

Or skip the install entirely and load it straight from a CDN — see "CDN (jsDelivr)".

## Files

- `src/open-analytics.js` — the tracker. Sends `page_view` on load, `click`
  on any `[data-track]` element, and `search`/`form_submit` on form submit.
- `src/open-analytics-chart.js` — renders the daily page-views line chart
  used by the admin dashboard, given a `[{ day, total }]` series and
  Chart.js already loaded.
- `dist/open-analytics.min.js`, `dist/open-analytics-chart.min.js` —
  minified builds of the two files above, generated by `npm run build`.
- `examples/` — runnable, no-backend-required HTML pages demonstrating
  both files (see `examples/README.md`).

## CDN (jsDelivr)

No install, no build — point a `<script>` tag straight at the published
npm package via jsDelivr:

```html
<script src="https://cdn.jsdelivr.net/npm/@cuongcds/open-analytics@0.1.0/dist/open-analytics.min.js"
	data-endpoint="/analytics/track"></script>
```

```html
<script src="https://cdn.jsdelivr.net/npm/@cuongcds/open-analytics@0.1.0/dist/open-analytics-chart.min.js"></script>
```

Pin an exact version (`@0.1.0`) for production; drop the version (`@cuongcds/open-analytics`)
to always get latest, or use `@0` / `@0.1` to float within a semver range.
See [jsDelivr's npm docs](https://www.jsdelivr.com/documentation#id-npm) for
every URL variant (unminified `src/`, a specific commit, etc.).

## Usage

Drop-in, auto-tracking (reads config from the script tag's own attributes):

```html
<script src="open-analytics.js"
	data-endpoint="/analytics/track"
	data-track-attribute="data-track"
	data-search-input-selector='input[name="q"]'></script>
```

Programmatic:

```html
<script src="open-analytics.js"></script>
<script>
	OpenAnalytics.init({ endpoint: '/analytics/track' });
	OpenAnalytics.track('signup_click', { label: 'header-cta' });
</script>
```

Mark any button/link you want click-tracked:

```html
<button data-track="resize_download">Download</button>
```

### Cross-domain endpoint

`endpoint` accepts a full URL on a different domain, e.g. a shared
analytics service behind several sites:

```html
<script src="open-analytics.js" data-endpoint="https://analytics.example.com/track"></script>
```

The tracker automatically requests `credentials: 'include'` for a
cross-origin endpoint (same-origin keeps `'same-origin'`), so the visitor
cookie is sent. That only works if the endpoint's response also grants it:

```text
Access-Control-Allow-Origin: https://your-site.com   (the exact origin, never "*")
Access-Control-Allow-Credentials: true
```

`ci3-analytics` supports this out of the box via
`$config['analytics']['cors']['allowed_origins']` — see its README.
`navigator.sendBeacon` (used whenever available) always sends cookies to
the target origin regardless of CORS, so this mainly matters for the
`fetch` fallback.

## Config

| Option                  | Default            | Notes                                                        |
| ------------------------ | ------------------- | ------------------------------------------------------------- |
| `endpoint`               | `/analytics/track`  | Where events are POSTed (`sendBeacon`, falls back to `fetch`) |
| `trackAttribute`         | `data-track`        | Attribute read for the click event's `label`                  |
| `searchInputSelector`    | `input[name="q"]`   | If a submitted form has a match, fires `search` instead of `form_submit` |
| `autoTrackPageView`      | `true`              | Fire `page_view` on load                                       |
| `autoTrackClicks`        | `true`              | Attach the click listener                                      |
| `autoTrackForms`         | `true`              | Attach the submit listener                                     |

## Chart

```html
<canvas id="analyticsDailyChart" height="80"></canvas>
<script src="https://cdn.jsdelivr.net/npm/chart.js@4.x/dist/chart.umd.min.js"></script>
<script>window.OPEN_ANALYTICS_DAILY_SERIES = [{ day: '2026-09-01', total: 12 }];</script>
<script src="https://cdn.jsdelivr.net/npm/@cuongcds/open-analytics@0.1.0/dist/open-analytics-chart.min.js"></script>
```

Or call `OpenAnalyticsChart.render(canvasId, series)` yourself once your
data is ready.

## Building

```bash
npm install
npm run build
```

Regenerates `dist/*.min.js` from `src/*.js` via terser (no bundling — each
file minifies 1:1, since both are meant to stay drop-in `<script>` tags,
not bundle entry points).

## Releasing

1. Bump `version` in `package.json` (semver).
2. `npm run build` — commit the regenerated `dist/*.min.js` (published/CDN'd
   files, unlike a typical npm package that builds on `prepublishOnly`,
   since jsDelivr serves whatever's committed under `dist/` at that tag).
3. `git tag vX.Y.Z && git push --tags`
4. `npm publish --access public`

jsDelivr needs no separate release step — `cdn.jsdelivr.net/npm/@cuongcds/open-analytics@X.Y.Z/...`
resolves directly from what's published to npm, live within minutes.

## Payload

Each event POSTs (as form-encoded fields):

- `event_type` — `page_view` | `click` | `search` | `form_submit` (or any custom string passed to `track()`)
- `path` — `window.location.pathname`
- `referrer` — `document.referrer`
- `label` — event-specific (the `data-track` value, the search keyword, the form name/action)

The backend is expected to resolve/attach a visitor id (e.g. via a cookie)
and store `created_at` — this library does neither, by design, to stay
backend-agnostic.
